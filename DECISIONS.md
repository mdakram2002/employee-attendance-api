# DECISIONS.md

1. **Indexes.** I create a unique index on `employees.emp_code`, which guarantees that employee codes are unique even under concurrent create requests. I also create a unique compound index on `attendance_logs(emp_code, date)`, which ensures one record per employee per attendance date and prevents duplicate punch-ins for the same attendance day. I keep a compound index on `(date, emp_code)` for fast listing and an index on `(emp_code, punch_in, punch_out)` for the open-record lookup during punch-out. I considered a broad compound index on `(status, date)` only because it helps some filtered reads; it is useful but not critical to correctness, so I keep it modest and let the app remain simple.

2. **Punch-in race.** If two identical punch-in requests arrive together, both fetch the same employee record, build the same attendance-day key, and both try to insert the same `(emp_code, date)` document. MongoDB enforces the unique index atomically, so exactly one insert succeeds with 201 and the other gets a duplicate-key error, which is converted to 409. That is the required concurrency guarantee; the app does not rely on a check-then-insert loop.

3. **Ties.** The leaderboard uses competition ranking: employees are grouped by total late minutes, then ranked with `$rank()`. If two employees tie at the cutoff, both rows remain in the result because the filter is applied after ranking: `rank <= limit`. That means the response can be larger than `limit` when ties sit at the cutoff, which is exactly how the assignment describes the intended behavior.

4. **Headcount.** Department summary computes a headcount from the `employees` collection by matching `joined_on <= month_end` and, if needed, the chosen department. This ensures employees with zero logs are still counted. The attendance-side aggregation is then joined only for employees who actually exist and joined on time, so the count is not lost when there are no records.

5. **One thing I would change** if this had to serve 100x the data. I would move the department trend and leaderboard calculations into a pre-aggregated reporting layer or materialized summaries keyed by date/department, so the app can answer heavy reads without scanning large attendance logs on every request. The code itself is correct for the assignment, but the next scaling step would be to precompute and refresh the summaries instead of doing broad live aggregates at request time.
